## 1. Problem statement

> Investigate the effectiveness of SBERT-based sentence embeddings for predicting story points of later issues from the same project using chronological splitting.

Story points express the relative effort of a software issue. Given an issue's text (title and description), the model predicts its story point value. Training and testing issues always come from the **same project** (within-project), and the test issues are always **newer** than the training issues (temporal ordering).

## 2. Objectives

1. Measure how well SBERT sentence embeddings predict the story points of later issues of the same project.
2. Evaluate with **Mean Absolute Error (MAE)** and **Median Absolute Error (MdAE)**, reporting five-fold validation results separately from final held-out test results.
3. Compare against simple baselines trained on exactly the same splits, so that any gain can be attributed to the representation and model.
4. Keep every step reproducible: configuration, seeds, split manifests and versions are recorded.

## 3. Dataset

- **Source:** TAWOS, https://doi.org/10.5522/04/21308124 (issues from open-source Jira projects, MySQL release).
- **Extraction** (`extract_data_from_sql_v3.py`): issues with a story point, a creation date, a non-empty `Resolution`, `0 < story point <= 100`, and with story point, title and description **not changed after estimation**, plus non-empty text.
- **Preprocessing** (`src/preprocess.py`): input text = title + blank line + description text; HTML/Jira markup removed; story points below 1, very short texts and duplicate issue keys dropped.

| Stage | Issues |
|---|---|
| With a story point | 65,427 |
| After extraction filters | 41,307 |
| After preprocessing | **39,588**, in **39 projects** |

No project is excluded for size (`min_issues: 0`). Projects with fewer than 30 test issues are flagged as *not reliable* in all summaries (4 of 39). The full filter funnel is in `data/reports/filter_funnel.csv`. Project coverage against the 39 projects named in the project guidelines is in `results/summary/project_coverage.csv`.

> The TAWOS data are **not** included in this repository. Obtain the MySQL dump from the link above.

## 4. Method in brief

| Step | What is done |
|---|---|
| Representation | `sentence-transformers/all-MiniLM-L6-v2` (384-d, L2-normalised, frozen, max 256 word pieces) |
| Split (per project) | Sort by creation date; oldest **80%** = development, newest **20%** = held-out test |
| Validation | **Rolling-origin**: development set cut into 6 chronological blocks; block 0 is train-only, blocks 1 to 5 are each validated once on all earlier blocks, giving **5 validation folds** |
| Model | 3-layer 1-D CNN (Conv1D 16-32-64, kernel 3, BatchNorm, ReLU, dropout 0.3, global average pooling, FC 64), L1 loss, Adam |
| Model selection | Learning rate from {1e-3, 3e-4} by mean validation MAE (development data only) |
| Final model | Retrained on all development rows, scored **once** on the test set |
| Baselines | Median predictor; Ridge on SBERT; kNN (cosine, median of neighbours) on SBERT; TF-IDF + Ridge |
| Metrics | MAE, MdAE: per fold, per project (macro), and pooled over all test issues |

**Why rolling folds?** The guidelines ask for five folds with every fold used once for validation. Training on later issues to predict earlier ones would break chronological order, so forward-chaining folds are used instead. Early folds train on little data and are noisy.

## 6. Setup

```bash
python -m venv .venv

pip install -r requirements.txt
```

The first run downloads the SBERT model (about 90 MB), so it needs internet access once.

## 7. Reproducing the experiments

**Step 0: extract the data** (needs the TAWOS MySQL dump loaded into a local MySQL server):

```bash
# Windows PowerShell
$env:MYSQL_PASSWORD = "your_password"; $env:MYSQL_DATABASE = "TAWOS"
# Linux / macOS
export MYSQL_PASSWORD=your_password MYSQL_DATABASE=TAWOS

python extract_data_from_sql_v3.py
```

This writes `data/raw/sbert_project6_issues.csv` and the diagnostics in `data/reports/`.

**Step 1: run the whole pipeline:**

```bash
python run_all.py                           # all projects, all stages
python run_all.py --project alloy_framework # one project (quick smoke test)
python run_all.py --from-stage train_cv     # resume after a failure
python run_all.py --dry-run                 # print the commands only
```

Stages, in order: `env_info`, `preprocess`, `make_splits`, `extract_embeddings`, `train_cv`, `evaluate_test`, `baselines`, `summarize`, `coverage_report`, `make_plots`. Each can also be run alone with `python -m src.<stage>`. Pass `--config path/to/ps6.yaml` if your config is not found automatically.

**When you change something, delete the stale outputs first:**

| You changed | Delete, then re-run from |
|---|---|
| Extraction filters | everything, then Step 0 |
| `min_issues`, split scheme, `n_blocks` | `data/splits`, `results`; from `make_splits` |
| SBERT model or text cleaning | `data/embeddings`, `data/splits`, `results`; from `preprocess` |
| Model, learning rates, epochs | `results`; from `train_cv` |
| Summary or plot code only | nothing; re-run `summarize`, `make_plots` |

**Record the environment** (also done by `run_all.py`):

```bash
python -m src.env_info --write-requirements   # writes results/environment.json + requirements.lock.txt
```

## 8. Configuration

Everything that affects results lives in `configs/ps6.yaml`: random seed (`42`), SBERT model name, CNN architecture, learning-rate grid, epochs and early-stopping settings, split ratios, rolling-fold settings, story-point range and the reliable-project threshold. Edit the YAML, not the code.

## 9. Outputs

| File | Content |
|---|---|
| `results/five_fold/<project>.csv` | Every learning rate x validation fold: MAE, MdAE, epochs, early-stop source |
| `results/test/<project>.csv` | Held-out test MAE/MdAE, selected lr and epochs, median baseline |
| `results/baselines/*.csv` | Baseline validation and test results, per project |
| `results/summary/comparative_table.csv` | **One row per model**: validation and test MAE/MdAE (macro and pooled), wins, rank |
| `results/summary/paired_comparison.csv` | CNN vs each baseline, per project, with Wilcoxon p-values |
| `results/summary/project_results.csv` | CNN validation (mean ± SD over folds) and test results, per project |
| `results/summary/guideline_table.csv` | The guidelines' table (SBERT + CNN row) |
| `results/plots/*.png` | Model comparison, per-project, validation-vs-test and scatter plots |
| `results/models/<project>.pt` | Final CNN of each project (used by `predict.py`) |

Five-fold validation results (`results/five_fold/`, `five_fold_summary.csv`) are kept separate from the final test results (`results/test/`, `test_results.csv`).

## 10. Results summary

Macro average over the 39 projects (7,919 test issues in total); lower is better. **Single run, seed 42.**

| Model | Test MAE | Test MdAE |
|---|---|---|
| kNN (SBERT) | 1.817 | 1.244 |
| **CNN (SBERT), assigned model** | **1.857** | **1.395** |
| Median (constant) | 1.872 | 1.436 |
| TF-IDF + Ridge | 2.041 | 1.399 |
| Ridge (SBERT) | 2.100 | 1.510 |

The CNN's MAE is within 2% of the median predictor's in 30 of 39 projects, so SBERT + CNN adds no measurable gain over a constant prediction in this setting. kNN on the same embeddings is the best model, about 3% better than the median predictor. Limitations (single seed, small test sets for some projects, filtering choices, no duplicate check) are discussed in the report.

## 12. Troubleshooting

| Message | Fix |
|---|---|
| `old make_splits version` / `manifest yields N validation folds` | Stale splits: delete `data/splits` and `results`, re-run `make_splits` |
| `missing embeddings or splits` | An earlier stage did not finish: re-run from `preprocess` |
| `No raw CSV found` | Check `data/raw/sbert_project6_issues.csv` and `data.raw_file` in the config |
| `ModuleNotFoundError` | Activate the virtual environment and run `pip install -r requirements.txt` |
